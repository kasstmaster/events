# Private guest sign-in and secure activation

Hosts keep email/password and approval-based registration. Family members keep assigned credentials and permissions. Guest sign-in now uses a permanent individual private URL, First Name, Last Name and the existing four-digit Household ID, followed by SMS proof for every new browser session. No username, separate guest password, email registration or Forgot Username control is required.

## Private links and access

Each adult's existing global identity has one random 256-bit URL ID, independent of public IDs and address credentials. The URL is `/guest#<private ID>` on the canonical Events origin. The fragment never enters HTTP paths, query strings or referrers. The browser sends it only in a same-origin POST body, keeps drafts in memory and clears it from browser history after authentication. Do not add analytics, request-body logging, or third-party scripts to this page. No credential is written to browser storage.

The database stores a SHA-256 lookup hash and an AES-256-GCM encrypted token with identity-bound authenticated data, never the plaintext ID. Ordinary host/contact/card/preview/export projections do not include either value. The owner can view/copy their own link in Settings → Private sign-in. Only a password-confirmed platform administrator can retrieve or reset someone else's link through Hosts → Guest sign-in access. Reset requires current record version and exact guest name, generates a fresh ID and revokes all that identity's guest sessions and outstanding codes. Existing links remain stable on ordinary reads and sends. Key/decryption failures fail closed; they never silently regenerate links.

Address Book → adult Contact actions → Send / Resend sign-in link submits the existing link directly to that person's **verified** phone using the shared one-shot transport. Hosts cannot choose its destination, see the URL or reset it. A provider acceptance or uncertain result is not confirmed delivery. No automatic retry occurs. Regular family accounts cannot send or administer these links.

## Verification and enrollment

A private URL alone never authenticates anyone. The server validates the URL, exact normalized names and current Household ID before sending a random six-digit code to the verified account phone. It returns no complete phone number or code. Store only an HMAC of the code, expire it after ten minutes, allow at most five guesses, supersede prior challenges on resend, enforce a 60-second resend cooldown and five sends per identity/hour, and apply persistent IP limits. Verify current identity, address credential, private-link version, verified-contact version, deletion state and challenge state transactionally before consuming the code and issuing an existing secure session. Different names or sibling identities cannot use another person's page or code.

A pre-existing recovery phone qualifies only when its stored verification is true. Host-entered contact phones, RSVP consent, unauthenticated input and browser fingerprints never prove phone ownership. Without a verified number, sign-in stops for administrator-assisted enrollment. The administrator must verify the intended guest and phone ownership outside this sign-in attempt, obtain authorization for security texts, confirm their own current password, and save the versioned verified contact. That action revokes guest sessions/challenges. Merely checking a box without completing that real-world verification is not enrollment proof. Do not use live accounts or messages to test this process.

Guest Settings → Private sign-in → Sign out other devices revokes that identity's other guest sessions and pending challenges, keeping the current session. Existing valid authorized sessions remain signed in without another SMS. Expired/revoked browsers repeat the private-page and SMS flow. The existing exact-Origin, HttpOnly, SameSite=Strict, HTTPS Secure, server-side expiry and origin-binding protections remain.

## Operator prerequisites — no production settings changed

Before separately approving guest-authentication rollout, securely configure **`GUEST_LINK_ENCRYPTION_KEY`** on the existing `events` Worker as a Secret: exactly 64 hexadecimal characters representing 32 cryptographically random bytes. Generate/store it in a secure secret manager; never paste it into chat, source, logs, command history or GitHub variables. Keep a recoverable private backup with database backups. Losing/changing it makes existing encrypted links unreadable; this implementation does not provide automatic key rotation. Do not replace it casually.

SMS remains disabled in the checked-in/default configuration and no runtime settings are changed by this feature. The existing separately approved `SMS_ENABLED`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`, signed webhook and STOP setup must work before new-device sign-in can operate. Enabling SMS also enables other already implemented message flows, so it requires a separate provider/release decision; do not enable it as an incidental test step. Missing key/provider/verified contact or an opted-out phone fails closed, creates no future messaging backlog and leaves valid existing sessions usable. Guests without phone access need administrator-assisted recovery; there is no household-code-only fallback.

## Migration, rollback and verification

All schema/records are additive. No guest identity, address credential, invitation, RSVP, profile, content, route, binding, namespace, object name or cron is rewritten for rollout. Children remain associated records and do not sign in independently. Old name/code, suffix recognition, code-claim and username/code HTTP authentication paths fail closed; host/family paths remain. Optional host-account attachment now requires an already authorized guest session; knowing a legacy username and Household ID is insufficient. Legacy username data/recovery records remain stored for compatibility, but no longer authenticate new guest sessions. Account/profile matching and permissions remain separate from authentication.

Do not roll back to code accepting only names/Household IDs or private usernames as proof. If rollout is paused, retain the additive records and encryption key, disable SMS only with an operator decision, and preserve valid sessions. Never restore insecure login as recovery. Link reset/contact correction is a scoped administrator action, not a duplicate-account registration.

`test/guest-auth.test.js` exercises real HTTP activation, secrecy, OTP limits/expiry/reuse, stale credentials, revocation and direct delivery with a mock provider; it also runs the unmodified production Worker and SQLite Durable Object with an intercepted SMS destination. `test/guest-auth-mobile.js` covers the real three-field/OTP/Settings UI on phone and desktop. Other feature/runtime regressions explicitly provision already authorized synthetic migration sessions through test-only helpers; the production Worker imports none of those helpers. No real provider, production endpoint, guest or deployment is used. Local tests do not establish live SMS delivery, phone ownership, key configuration or production deployment.
