# Automatic Events release safeguards

Only the owner merging an approved PR into `main` may start an automatic production release. Feature pushes, direct pushes, open/updated/unmerged PRs, previews and schedules do not deploy. The automatic and existing manual workflows share the `events-production` concurrency lock. This correction does not merge, deploy, change credentials or modify Gather application code. It restores the deployment configuration exactly from approved application merge `925c25ad0f89b6deb85838ae36f13d168444b1d0`, retaining its account, both runtime flags, variable retention and existing five-minute cron.

A failed verification does not mean deployment was rolled back.

The recovery artifact `events-auto-recovery-42925146980-1` records previous Worker `2445780c-00a8-4be8-be81-64e450420038`, both required compatibility flags and an approximate SQLite recovery timestamp of `2026-11-10T23:40:46.000Z` (expires `2026-12-10T23:40:46.000Z`). The deployed main configuration omitted `global_fetch_strictly_public`. The previous live settings in the checkpoint contained it. `safeSettings` rejects the missing flag with `Runtime date/flags differ from the approved release.` The old automatic error handler masked that fixed validation error as a transport failure. A synthetic regression reproduces the rejection and proves the actual safe reason is now reported. The failed run produced no post-verification artifact, so this investigation does not claim a fresh complete live settings inventory.

More significantly, main is still the historical operations branch with an older application. At investigation time its head was `da5b68bc6d8af8d60badc4b8fe689f91c32b6c6d`; it did not contain approved application merge `925c25ad0f89b6deb85838ae36f13d168444b1d0`. Passing the small tests present on that older branch did not establish that it was safe to replace the current application.

## What the correction enforces

- Check out the exact owner-merged commit with full history. Prove that it includes the approved application history and that tracked files remain unchanged, both before validation and immediately before production access. The historical application SHA is an ancestry floor, never a deployment target. Later approved commits are deployed dynamically from the merge event. Once production has a full SHA annotation, reject older/divergent queued releases and already-active commits; the concurrency lock alone does not prove deployment order. Legacy manual versions without SHA annotations still require the source/configuration guards.
- Run `npm ci` and `npm run format:check` before any production access. Fix the automatic helper/test formatting and include both in the PR safety workflow.
- Validate the reviewed account, Worker entry point, compatibility flags/date, worker/preview settings, variable retention, assets binding, sole SQLite class/migration and recovery cron. Unexpected routes/environments fail closed. The unsafe historical configuration is rejected in regression tests; the corrected file retains the reviewed production footprint without changing application code.
- Retain unit/release, browser, actual Cloudflare runtime and dry-run build gates. Preserve the manual workflow's exact pin, prior-version guard, checkpoint upload and verification behavior.
- Read existing settings, active deployment, immutable migration evidence, cron and worker/preview settings; require closed setup. Take a second stable snapshot and upload the timestamp-based recovery checkpoint before publication. No household, event, guest or content records are retrieved or mutated by these helpers.
- Preserve `--keep-vars`, target only `events` in the reviewed account, and attach the full merged SHA as the Worker version message. Wrangler's bounded structured output supplies the expected new version. Raw structured output is not uploaded or logged.
- Verify that exact version is active at 100%, its message identifies the merged SHA, setup remains closed and runtime/binding/variable fingerprints and cron remain unchanged. A different new version cannot satisfy verification. Retry only transient GET failures or delayed activation, at most four attempts; never retry deployment or permanent settings/authentication failures.
- Print fixed, typed validation errors and numeric HTTP statuses only. Never print token/header values, private settings, raw provider bodies or exception messages. Missing checkpoints/output and malformed responses produce specific safe errors.

## Owner actions before automatic release can work

1. Integrate the approved application history into main through an owner-reviewed PR, retaining this correction’s approved deployment configuration. Do not merely copy the old application tree or switch automatic deployment to a hardcoded application checkout. This deployment-only repair deliberately does not copy or change application features. Until the reconciliation is reviewed, the ancestry guard blocks production access.
2. Review live settings read-only after the failed deployment, including both runtime flags, the original cron, closed setup, binding identity and routes. Current runtime state and any necessary restoration require separate owner review. A missing required flag/cron stops preflight; do not weaken the check or blindly rerun an old deployment. The manual backup remains available but its recorded prior-version guard may correctly reject a changed live version; any backup release pin/baseline update requires its own review.
3. Enforce required checks for main in **Settings → Rules → Rulesets** (or branch protection): require pull requests and successful `test` and `safety` checks, plus any additional application browser jobs after integration. The branch API reported `protected: false`, and the ruleset listing was empty during investigation. Protected-branch details require administration permission unavailable to this connection. The workflow's own gates protect publication, but they are not a substitute for required PR checks.
4. Create the PR from the supplied feature branch, review its diff and GitHub checks, then merge yourself when ready. Do not use a test merge or manually dispatch a deployment to validate this repair. A deployment after these changes remains unverified until an owner-approved release actually runs successfully.

Keep the existing GitHub `CLOUDFLARE_API_TOKEN` secret. No token rotation, Mac installation, paid upgrade, gateway deployment, other repository/site change, SMS enablement or live test fixture is required. Cloudflare build previews must remain disabled; this policy permits only the owner-controlled merge-trigger workflow.
