# Visual defaults, address codes and full-page cards

This follow-up starts from application `3fe6985fc491dc722077b1d407261b06cee275f7` on `feat/household-subdomains`. It changes only the shared events application and its existing data model. The owner authorized the four-digit, address-scoped credential and shared-address RSVP changes during implementation; these replace the previous permanent individual-code behavior.

## Final behavior

- Page defaults use the actual application renderer and layout pass with browser-only synthetic state. Separate host/guest event examples include artwork, When, Where/address, deadline, registries/uploads, correct role actions and navigation. Host/guest sign-in, registration and family page examples use the same live components. Phone/tablet/desktop previews have independent viewport widths. There is no tenant lookup or synthetic account/response write. A scriptless, form-disabled sandbox contains the examples.
- Double-click interface wording and type directly. Changes mirror across that wording’s uses in the draft. Enter finishes and Escape cancels the current inline edit; Save commits defaults. Host-owned example names, titles, descriptions, addresses and notes are protected content. Formatting roles and structured position controls remain shared, and changing platform defaults still preserves existing household/event formatting.
- An address has a random four-digit code, including leading zeroes, shared by every guest explicitly assigned to that household-scoped address. Unassigned guests have an individual fallback. Address text edits keep the code; moving a guest gives them the destination’s code, removes old credential access and revokes their identity sessions. Stable identity, invitations and responses remain. Retired codes are reserved; the finite 10,000-group space fails closed on exhaustion. Legacy individual codes remain aliases only until their original entry moves; aliases are not copied to other hosts.
- Any invited adult can RSVP for invited adults/children sharing that event relationship’s address. Blank or omitted people remain unchanged; unanswered people stay unanswered. Separate per-adult versions and claims are retained. An affected stale response rejects the whole group transaction. Other addresses’ contacts, names and responses remain excluded. Designated-adult and capacity/deadline rules still apply.
- Add/Edit guest contains address search by title/street, explicit match selection, inline shared-address editing and new-address creation. Address and guest changes save atomically with both record versions. Cancelling, stale versions and invalid guests cannot leave a partial address behind. The separate Add address section is removed.
- Cards/templates open as a full-page editor. A side palette lists every variable, including optional Address invite code. Variables support drag-to-canvas and button insertion; selecting an item exposes its own font, color, size, alignment and position controls. Dragging snaps bounds to center/edges; a selected corner resizes the item. Numeric controls and arrow keys provide alternatives. Phone tools use a side drawer. Selection handles and guides never enter exports/print.
- Address invite code is never added automatically. A host-owned recipient and an explicit `recipient.inviteCode` field are required to snapshot the code into a private card. Shared templates store the variable definition, not a recipient’s code. Saved cards keep existing snapshot semantics; review new invitations after a move. Household link/QR destinations remain unchanged.
