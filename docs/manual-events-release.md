This manual-only workflow deploys release `3fe6985fc491dc722077b1d407261b06cee275f7` to the existing `events` Worker in account `37d068144865a0b725ee272bc7b2eb71`. It never deploys the gateway, changes automatic/preview build settings, creates credentials, sends messages or resets storage. The helper is checked out from the workflow commit separately from the approved application release, so new safety checks run without changing the approved application code.

Before running, production/preview builds must remain disabled. These controls were inspected while preparing this correction; production uses `feat/cloudflare-deployment`, Disable builds is checked and preview branch builds are off. Recheck them if settings have changed. The workflow does not enable them.

Open **Actions → Deploy events manually → Run workflow**, selecting the branch containing this correction after review. The existing GitHub Actions secret `CLOUDFLARE_API_TOKEN` is used. No local Mac installation or OAuth is needed. Authentication is checked using read-only requests against the actual events account, rather than a user-token-only verification endpoint (which may reject account tokens). A missing/invalid secret or insufficient permission stops before deployment.

The helper verifies the existing `EVENTS_DATABASE` namespace ID, implementing class/script, ASSETS, disabled SMS, runtime flags/date, closed setup and the reviewed previous production version. It checks the live version's `events-v1` migration tag through the Worker-scoped version endpoint. The exact namespace and reviewed production version identify the previously verified SQLite backend created by that migration's `new_sqlite_classes` entry; storage type is immutable. This uses the reviewed SQLite baseline, not a fresh account-wide namespace inventory. The existing per-Worker token cannot list namespace inventory, so the workflow does not request broader permissions or call account-wide database endpoints. An unknown version, changed namespace/class/script or different migration tag stops the job.

The helper saves only selected metadata and hashes of plain-text variable values, never raw settings, secrets or guest data. GitHub must successfully retain the checkpoint artifact before the deployment step can run. A failed upload stops the job.

If an active token receives HTTP 401, verify its `not_before` and expiration times using Cloudflare's account-token verification endpoint before replacing it. An active token with a future start date still rejects Worker requests. The release token's initial start date was corrected from November 1 to October 31, 2026, with its expiration and per-Worker Editor scope unchanged. HTTP 403 on an account-wide namespace request is a scope mismatch, not proof of a bad token value.

## Timestamp recovery checkpoint

Cloudflare's [SQLite Durable Object PITR API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#pitr-point-in-time-recovery-api) supports recovery of an entire object's SQL and key-value contents within 30 days. `getBookmarkForTime(timestamp)` resolves an approximate timestamp to a recovery bookmark. The workflow records Cloudflare server time, the existing namespace/object name and prior deployment version immediately before release. It does **not** claim to capture an exact current bookmark or export a database backup. This is a timestamp-based whole-object recovery checkpoint, not a frozen exact application revision. An exact bookmark would require a separately reviewed private operation inside the live Durable Object; no such endpoint is introduced here.

The artifact is `events-recovery-<run-id>-<attempt>` and is retained for 29 days. Its recovery timestamp expires after 30 days. Access to the artifact alone cannot restore data. Restoration requires privileged code running inside the same existing object and separate explicit owner authorization; the workflow never restores data automatically. Do not use `wrangler d1` commands: this is a Durable Object, not D1.

For an authorized recovery, first review and pause background writes as described in the approved release's `docs/shared-editors.md`. Have the operator resolve the saved timestamp using `ctx.storage.getBookmarkForTime(new Date(timestamp))` **inside the existing EventsDatabase object**, then use the documented `onNextSessionRestoreBookmark` and restart sequence only after reviewing possible loss of later writes. Preserve namespace, class, object name, additive tables, retired claims and deletion protections. This workflow adds no public restore route and performs no database import/reset. The previous code version alone is not a data restore and must not be blindly rolled back if it ignores new deletion protections.

The gateway is not deployed by this release. The approved source records gateway version `0f6aaacb-713f-43ba-b742-5818f9ae1830` as its historical reference; that is not a fresh live observation. Current gateway-account access was unavailable during this correction, so current gateway version remains unverified. This workflow does not claim to complete that release-guide check or interactive live acceptance tests.

After deployment, automatic verification checks a new active version, closed setup and preserved bindings/variables/runtime flags. Complete canonical and household sign-in, opaque links/QR, guest RSVP, existing content, editor inheritance and cards using existing authorized sessions. Do not delete real accounts or send live texts as tests. Post-deployment failure does not mean nothing changed; inspect the run and checkpoint before any recovery. No automatic rollback runs.

Validation for this workflow correction uses synthetic API responses with `node --test scripts/manual-events-release.test.mjs`. It does not rerun application tests or claim to verify the live GitHub secret before the owner runs the workflow.
