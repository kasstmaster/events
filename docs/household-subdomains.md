## Shared registration and immutable claims

The entire entered name generates the address immediately: `Dubois` → `dubois.ilymmd.com`, `Raudman` → `raudman.ilymmd.com`. There is an address preview, **no separate domain input**. No inserted “the”, pluralization, added words or numbered alternatives. Hosts cannot edit a domain during registration, in settings or through the API.

Browser and server share `public/household-address.js`: Unicode NFKD; remove combining accents U+0300–U+036F; lowercase; remove straight/curly apostrophes; replace other non-ASCII letter/digit runs with a hyphen; trim hyphens; truncate to 63 characters; trim trailing hyphens again. `server/household-domains.js` validates the final ASCII DNS label (3–63 letters/digits/internal hyphens, no `xn--`, no reserved site/platform name). Unsupported/short names require another household name. No surname extraction occurs. Normalization may collide.

Availability is debounced 400ms, advisory, rate limited and ignores stale responses. Successful approved registration atomically creates the user/household, claims the case-insensitive label, enqueues its routing job and consumes approval. Competing, reserved, retired or invalid claims fail without partial accounts or consumed approval. The server derives the label independently and rejects arbitrary overrides.

Existing households/claims/slugs are never renamed or backfilled. Later display-name edits preserve their original address. Legacy unclaimed accounts retain their opaque links. Historical retired labels stay permanently reserved; no host rename capability remains. Existing QR/opaque `/h/<slug>` links remain compatible. Event appearance never changes household guest-login appearance.

## Automatic provisioning service

`cloudflare/household-provisioner.js` runs from the **existing `EventsDatabase` Durable Object's alarm**. The additive `household_routing` table in the same authoritative SQLite database stores a transactional outbox, ownership, a random resource marker, private probe, resource receipts, phase, attempt count, retry time, safe error code and verification time. It contains no Cloudflare credential. New registrations enqueue work even while automation is disabled, without backfilling existing households.

The adapter arms the alarm after registration and on object initialization. An existing alarm is not postponed. One job is processed per alarm; the next due job is scheduled. Errors are persisted with 30-second exponential backoff capped at one hour. A recovery alarm is armed before external work; a new five-minute Cron Trigger wakes the same named object in case alarm scheduling/worker interruption stranded the outbox. Disabled automation makes cron a no-op and stops alarm work. There is no public provisioning endpoint or administrator bypass, no second application/database/DO namespace, and no email/host routing request.

For an authoritative current, non-retired claim only, the service:

1. Fetches complete paginated DNS, Workers routes and custom-domain inventories from the fixed domain account/zone. Malformed/incomplete responses fail closed. Matching wildcard DNS, any conflicting route (including null-script exclusions), exact DNS owned by anyone else, or a custom domain blocks provisioning. Reserved labels fail before requests. Account/zone/script/API origin are code-pinned, never caller input.
2. Uses **POST only** to create an absent proxied AAAA `100::` record for the exact hostname, marked `events-household:<job-id>`, then the absent exact `hostname/*` route to `events-household-gateway`. It never updates/deletes an existing DNS record/route, rewrites Worker settings, changes bindings/secrets, enables a paid plan or adds a wildcard. Inventory is checked again between writes and after verification.
3. Stores resource IDs and recovers from a lost POST response/restart by recognizing its own unique DNS marker and the exact gateway route. It never adopts unrelated records. If an external administrator races a write, a conflicting/duplicate record blocks activation; this service leaves existing records untouched. Cloudflare has no transaction spanning DNS and routes; newly created partial resources remain owned/pending for retry, never automatically deleted.
4. Sets the job to `verifying`, then fetches the actual HTTPS hostname's private challenge, `/`, `/app.js`, `/household-address.js`, `/style.css` and `/api/public/context`. Public transport traverses DNS/TLS and the domain-account gateway. The response must match the unguessable per-job challenge and exact household ID; assets/root must match expected application content, and responses must have no cookies. Redirects, permission/rate/quota errors, TLS/DNS failures and mismatches leave it pending. Redirects are handled manually and rejected (Workers does not support `redirect:"error"`). No live sign-in/RSVP is performed.
5. Rechecks inventory/claim and marks the job active transactionally **only after all checks pass**. Sharing/new QR then selects the custom address. Until that point it selects the opaque link. Jobs already active are not reprovisioned. Routine host registration needs no domain field or manual routing request after the approved service is configured.

## Gateway and authentication

One stateless gateway in the domain account fetches only `https://events.kassandraraudman.workers.dev`. Exact per-host routes retain the browser hostname. No redirect or CNAME-only cross-account attachment is assumed.

`HOUSEHOLD_ROUTING_ENABLED=true` enables an authoritative, uncached routing lookup instead of per-registration Worker-setting writes: for a valid DNS label, the gateway signs a fixed `/api/routing/status` request to the exact origin. The events edge verifies HMAC before the existing database confirms that exact claim is active. Unknown/unclaimed/retired/pending names fail generically. The gateway forwards the user request only after approval; the app rechecks current claim state. Existing static `HOUSEHOLD_HOSTS` entries remain supported and are not replaced.

Before activation, only the service's 256-bit per-job probe permits the allowlisted anonymous GET verification paths. The signed status lookup and signed forwarded request bind that probe header. It cannot grant access to sessions, host/guest APIs or mutations; user authentication/invitation checks remain unchanged. Probe/receipt/credential data never appears in host API payloads or logs. The challenge endpoint requires verified gateway context and the exact private probe, even for active names. Direct canonical calls and forged forwarding headers fail.

HMAC binds method, fixed origin, path/query, hostname, time, nonce, Origin, cookie, Content-Type, If-Match, trusted client IP, optional probe and body hash. Legacy non-probe signature envelopes remain compatible. Requests expire after 60 seconds; mutation nonces are consumed persistently. Gateway body limit is 8 MB. Untrusted forwarding/Authorization headers are discarded. The gateway never fetches a caller-chosen origin or follows a redirect; there is no open proxy or broad CORS.

Host-only `__Host-events_session` cookies are Secure, HttpOnly, SameSite=Strict, Path=/ and bound server-side to the exact origin. Domain/legacy/insecure cookies are rejected by the gateway. Canonical sessions remain compatible on the canonical site only. Browser Origin is retained; sibling household Origins fail CSRF checks. A hostname is context, never authentication. Setup/admin/registration remain canonical-only; guest invitations, tenant isolation and name-only guest identity limits remain enforced.

## Rollback and partial failure

Disable `HOUSEHOLD_ROUTING_ENABLED` on the **app** to stop jobs, dynamic forwarding and custom-address sharing for automatic jobs; sharing falls back to opaque links. Disable it on the gateway too. Existing static allowlist behavior is retained; if withdrawing static forwarding, handle its entries explicitly. Keep newly created exact DNS/routes as owned generic-unavailable endpoints. Do not remove/repurpose them or release labels. Pending jobs and receipts remain for idempotent resumption; do not delete the outbox/table or restore older guest data over new RSVPs.

A token outage, quota, conflicting record or verification failure leaves the claim reserved/pending and retries with bounded backoff. Fix the narrowly scoped permission/resource problem after approval; registration does not need to be repeated. Partial DNS/route additions are left in place; the service never performs cleanup deletes. External changes can block a claimed name without making it active.

Prefer keeping the new code with automation disabled. If code rollback is approved, disable dynamic gateway forwarding **first**, then restore recorded previous versions in the same Workers/namespace. The older app cannot enforce the new dynamic boundary. Keep existing secrets/bindings/storage, additive tables, claim/retirement metadata and setup/session data intact. The previous UI allows independent domain editing again; consider that regression when reviewing rollback. No database migration reversal/reset is part of rollback.
