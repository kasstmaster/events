## Supported design

One application and one authoritative database remain in the events account. A new stateless `events-household-gateway` Worker lives in the domain account. It receives **exact per-host routes** such as `theraudmans.ilymmd.com/*`, backed by a new proxied AAAA `100::` placeholder for that hostname, then makes a normal HTTPS Fetch to the verified events workers.dev origin. The browser keeps its household URL. No redirects, CNAME-to-cross-account attachment, wildcard DNS record or wildcard Worker route are used.

Official documentation reviewed:

- [Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/): route prerequisites include a proxied DNS record; route specificity and matching apply. The gateway is a proxy in front of the separate application origin.
- [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/): custom domains attach inside an owned zone, match exact hostnames, and do not support wildcard domain matching. A CNAME by itself does not attach a hostname to a different account's Worker.
- [Global Fetch strictly public](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public): the gateway's explicit flag sends Fetch through the public Cloudflare front door rather than a zone-origin shortcut.
- [Fetch](https://developers.cloudflare.com/workers/runtime-apis/fetch/): normal HTTPS upstream requests. No cross-account Durable Object or service binding is assumed.
- [Build branches](https://developers.cloudflare.com/workers/ci-cd/builds/build-branches/): a push may invoke production or preview commands. Do not rely on Pages-specific skip-commit conventions to suppress Workers builds.

The public-Fetch architecture is supported by these routing primitives and passes the local two-Worker runtime tests. **Actual cross-account network traversal, DNS and TLS are not verified until a separately approved deployment is performed.** If the existing events origin is Access-protected, disabled, quota-limited or blocks Worker Fetch, stop before activation. Resolve the narrowly scoped upstream access issue with owner review; do not disable security broadly, migrate the database, move a Worker or replace any production resource. A concrete fallback is to retain working opaque `/h/...` links while arranging a verified public HTTPS endpoint for the same existing events Worker/database, then use the same restricted gateway. Moving live data is not the fallback.

## Claims, activation and renaming

`household_domains.label` is a case-insensitive SQLite primary key. Registration consumes the approved email and claims a label in one database transaction; later host-only edits claim/retire labels and update the versioned household record in one transaction. A losing simultaneous claim returns 409 and consumes neither approval nor household changes. Existing clients that omit `subdomain` retain their old behavior; the new registration form provides a random `household-…` suggestion, requires a chosen name, offers availability checking and never infers a surname. Existing households are not automatically assigned names.

Labels trim surrounding whitespace and fold ASCII letters to lowercase. They must be 3–63 ASCII letters/digits/internal hyphens, begin/end with a letter or digit, and cannot start `xn--`. Dots, Unicode/IDNA, underscores and reserved labels are rejected. There is no punctuation-to-hyphen rewriting. Availability reveals only a boolean and is persistently rate-limited; the save transaction is authoritative.

Claims are **pending** until the operator provisions that exact hostname and adds it to `HOUSEHOLD_HOSTS` in both Workers. Arbitrary claims do not magically create DNS. Pending addresses keep sharing the existing canonical opaque `/h/<slug>` link and QR. After activation, the shared link helper supplies the custom HTTPS root address to share/copy/native-share, guest-page links and newly generated invitation/download QR codes. Previously printed opaque QR codes continue to work unchanged. The app's `active` status means the operator has added the hostname to its provisioned allowlist; deployment verification is still required.

A rename permanently retires the previous label. Old custom addresses return the generic unavailable page; they never redirect or resolve to a new owner, including the former owner. The new label begins pending; old `/h/<slug>` addresses remain stable. Keep the old custom route/DNS and gateway allowlist entry in place to serve the generic page; never reuse it. A host who renames from their custom hostname returns to the main platform and signs in there. Hosts should continue sharing the stable opaque link until their new address is activated. Event appearance overrides never modify household login appearance.

## Trust and request handling

- Gateway accepts only HTTPS, a validated exact allowed hostname and supported application methods. Its upstream is one operator-configured exact `https://events.<account>.workers.dev` origin, never a request parameter/header. It forwards only application headers, overwrites client IP with Cloudflare's edge-provided value, and drops arbitrary forwarding/Authorization headers.
- HMAC-SHA256 covers version, method, upstream origin, path/query, household hostname, timestamp, random nonce, application headers (Origin, cookie, Content-Type, If-Match, client IP), and body hash. Both Workers need the same new `EVENTS_GATEWAY_SECRET` of at least 32 random characters. Do not put it in config, source, logs or URLs. HMAC requests expire after 60 seconds; mutations also consume a persistent nonce to reject replay. Request bodies are limited to 8 MB.
- Events public edge strips the private hostname header, verifies HMAC/allowlist/upstream, then supplies hostname context through its private existing DO binding. Client-supplied forwarding/household headers alone never authenticate. Once `EVENTS_ORIGIN` is configured, alternate canonical origins are refused.
- The shared handler resolves the active household claim before serving its page, assets or APIs. Unknown, unclaimed, retired and mismatched opaque household paths fail closed with a generic unavailable response. Unprovisioned hosts have no promised application page and may be DNS-unresolved; no wildcard intercept is added to manufacture a page for them.
- A hostname selects context, not identity. Guest name lookup, invitations and event authorization remain unchanged. Hosts can log in on only their own custom hostname; administrators and registration/setup use the main platform. Cross-household public slug lookups are rejected on custom hostnames. Name-only sign-in retains its documented identity limitation.
- Custom-host cookies are `__Host-events_session`, host-only, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`. New sessions are server-bound to their exact origin; legacy canonical sessions stay usable only on the canonical site. Canonical `events_session` cookies are retained for compatibility. Gateway refuses Domain/legacy/insecure cookies from upstream.
- Origin remains the actual browser Origin. The handler checks it against the verified external origin; sibling household origins fail CSRF checks even though they are same-site. No wildcard CORS or Origin rewriting is used.
- HTML, assets and APIs all pass through the gateway without URL replacement. Relative URLs remain same-origin. Redirect following is disabled; unexpected upstream 3xx responses fail with 502 rather than leaking cookies/signatures or changing the browser hostname. Responses are no-store; the shared CSP/security headers remain in place.

## Rollback and partial failure

- Before activation: leave/restore `HOUSEHOLD_HOSTS` empty in the app. Sharing/QR falls back to stable opaque links. If only one account deploy succeeds, do not activate either hostname. Existing events database remains authoritative; do not copy/reset it.
- To withdraw a live custom address, first remove its activation from the **app** allowlist so new shares/QR use the canonical link. Then replace its gateway behavior with the generic unavailable response (removing it from the gateway allowlist achieves this while its route remains). Existing explicit unrelated websites remain untouched. Retired labels remain reserved in SQLite; never delete them for rollback.
- Prefer retaining the reviewed application with custom hosts disabled, preserving all additive metadata and session-origin checks. Do not roll back to a pre-feature application while the gateway still forwards: the old app cannot enforce hostname scope and may expose the wrong household's UI.
- If application code rollback is required, disable household forwarding first, then restore the recorded previous events deployment/version in the **same** Worker/namespace. Do not roll back, rename or delete the Durable Object class/namespace or migration history, remove tables, restore an older database over newer RSVPs, or alter setup/account state. Pre-feature code ignores new tables, but loses origin-scoping for new sessions: perform that rollback only with explicit review of session implications; disabling custom hosts on the current version is the safer operational rollback.
- Gateway rollback affects only the new gateway. Keep exact retired-host routes/DNS serving generic unavailable pages to avoid takeover. Do not remove or overwrite any preexisting DNS/route. Deleting newly created routing resources or secrets is a separate reviewed cleanup, not a data rollback.
