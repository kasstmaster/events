# Home cards, options menu and removal of notes UI

The shared host Home page introduces Contacts first and Family Workspace second, each in its own themed container with a description and Open button, above event invitations. These destinations are no longer toolbar buttons. They keep the existing shared Contacts/workspace routes, permissions and data model.

Edit House/Edit Event, Share Household Link and Settings are shared three-dot actions across the applicable host pages. Settings also moves to the three-dot menu for guests, family members and the legacy administrator. Host bottom navigation is Home; guest event Print and existing administrator tools retain their permitted places. Existing sorting, creation, QR, event content tools and preview actions remain. Selecting an action closes the menu even after native sharing is canceled; Settings closes stale inline management first.

All dedicated household, event, contact and family-record note fields/sections are removed, including maintenance note text and note-based UI search matches. Existing stored notes/history are retained, private and unchanged by ordinary form saves. No data deletion or migration accompanies removal of the interface. Task instructions, event descriptions, custom details and user-created records remain supported. This supersedes earlier notes-editor descriptions in historical release handoffs.

Home cards render through the real shared page functions in administrator visual defaults. Isolate the example's administration context so a promoted host editing defaults sees the actual host Home instead of an administrator landing page. Keep the five appearance categories and existing design inheritance/overrides intact. Host-only destination cards do not expose private Contacts or Family Workspace to invited guests.

Validation uses synthetic local accounts/data and mocked native share/print only: 101 application/API tests, all six phone/desktop browser suites, actual Cloudflare Worker/SQLite runtime, formatting/whitespace and events Worker dry-run bundling. Browsers cover card order, moved menu actions, roles, sharing cancellation, notes UI absence and saved-note preservation, and promoted-host default examples. Wait for fresh GitHub checks before merge.

Release only the resulting reviewed application merge through the existing manually pinned events deployment workflow. Main remains the operations tree, not the application release. Record the current approved account/Worker version and upload a fresh recovery checkpoint before deploying. Preserve all data, bindings, namespace/class/object, secrets, runtime variables, routes and cron. Keep SMS and automatic production/preview builds disabled; never deploy the gateway or another website/repository. This UI follow-up does not activate AnyList, send messages, promote a real host or remove a real administrator. Those pending live actions still require the previously documented secure configuration/authenticated handoff.
