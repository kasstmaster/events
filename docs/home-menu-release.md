# Home cards, options menu and removal of notes UI

The shared host Home page introduces Contacts first and Family Workspace second, each in its own themed container with a description and Open button, above event invitations. These destinations are no longer toolbar buttons. They keep the existing shared Contacts/workspace routes, permissions and data model.

Edit House/Edit Event, Share Household Link and Settings are shared three-dot actions across the applicable host pages. Settings also moves to the three-dot menu for guests, family members and the legacy administrator. Host bottom navigation is Home; guest event Print and existing administrator tools retain their permitted places. Existing sorting, creation, QR, event content tools and preview actions remain. Selecting an action closes the menu even after native sharing is canceled; Settings closes stale inline management first.

All dedicated household, event, contact and family-record note fields/sections are removed, including maintenance note text and note-based UI search matches. Existing stored notes/history are retained, private and unchanged by ordinary form saves. No data deletion or migration accompanies removal of the interface. Task instructions, event descriptions, custom details and user-created records remain supported. This supersedes earlier notes-editor descriptions in historical release handoffs.

Home cards render through the real shared page functions in administrator visual defaults. Isolate the example's administration context so a promoted host editing defaults sees the actual host Home instead of an administrator landing page. Keep the five appearance categories and existing design inheritance/overrides intact. Host-only destination cards do not expose private Contacts or Family Workspace to invited guests.

Validation uses synthetic local accounts/data and mocked native share/print only: 101 application/API tests, all six phone/desktop browser suites, actual Cloudflare Worker/SQLite runtime, formatting/whitespace and events Worker dry-run bundling. Browsers cover card order, moved menu actions, roles, sharing cancellation, notes UI absence and saved-note preservation, and promoted-host default examples. Wait for fresh GitHub checks before merge.

Release only the resulting reviewed application merge through the existing manually pinned events deployment workflow. Main remains the operations tree, not the application release. Record the current approved account/Worker version and upload a fresh recovery checkpoint before deploying. Preserve all data, bindings, namespace/class/object, secrets, runtime variables, routes and cron. Keep SMS and automatic production/preview builds disabled; never deploy the gateway or another website/repository. This UI follow-up does not activate AnyList, send messages, promote a real host or remove a real administrator. Those pending live actions still require the previously documented secure configuration/authenticated handoff.

## Reading position and invitation headings

Background refreshes capture the current window position immediately before rendering refreshed data and restore it after the shared rendering/layout pass. This avoids scroll jumps caused by temporarily removing/reordering page content. Capture happens after network requests, preserving scrolling performed while a request is in flight. Explicit navigation retains its existing behavior; editor/draft guards and actionable connection failures remain in place. No live data or appearance defaults are rewritten.

The common event chooser renderer places the household logo or You’re invited to gather heading in a full-width row above event details and host action columns. Date/title/description/attendance/View Event stay left and RSVPs/Reminders/Cards/Invitation stay stacked right. Hosts, guests and administrator examples keep the same renderer and five-category formatting. Phone/desktop regression coverage checks the heading spans both columns; a synthetic server-side content update is adopted across polling cycles while the reader's scroll position remains unchanged.

## Live contact sync feedback and child ordering

The existing authorized host refresh carries the configured household's AnyList job status. Starting a sync disables duplicate starts and shows pending progress; completion updates contact rows and announces once without a manual status check or a routine connected/updated banner. It does not start additional jobs or poll AnyList directly. Existing generation, editing and selection guards preserve unsaved drafts and the reader's scroll position.

Within each address group, the shared Contacts renderer places adults before children while retaining their manual order within each category. Children use a distinct child icon and retain the designated-adult text. Manual movement stays within the same address and adult/child category. No guest ID, address code, parent association, invitation or RSVP is rewritten for presentation. Browser coverage forces a child to an earlier stored position and verifies the adult-first display and distinct icons; a synthetic background job completes and updates a contact without a manual status request.

## Confirmed contact uninviting

Uninvite Guests replaces the former uninvited-only filter. It enters selection mode over the existing Contacts list, then lets the host select an owned event and confirm the removal. In uninvite mode, selecting an adult includes their children; selecting a child does not select the adult. Unchecking a selected child clears its parent's selection so an adult cannot accidentally be removed while that child is retained. Cancel and navigation discard only the selection. Invite Guests keeps its existing additive behavior and child-to-adult selection rule.

Both endpoints require an event version, validate every contact against the authenticated household and transact the final invitation set. The shared event-invitation validator enforces designated adults and preserves every saved attendance answer, including children's answers. Attempting to uninvite any answered guest rejects the whole batch. No responses, claims, credentials, contacts, event content or sibling events are removed or rewritten. Conflicts retain selection and require a fresh choice/confirmation; no operation is automatically retried and no message is sent.

Regression coverage checks partial child removal, dependency and role failures, cross-tenant IDs, missing/stale versions, no-op removal, sibling/content/credential/response preservation and atomic rejection of answered guests. Phone/desktop browsing exercises confirmed removal from one event and a canceled confirmation with no writes.
