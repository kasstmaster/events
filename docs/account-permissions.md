# Central accounts and local contact permissions

Registered information belongs to the person, not to a host who adds them. Existing `person-account` authentication records, `personal-member` membership and `personal-household` family information remain the central source for registered guests/hosts. Existing host/system-admin credentials and assigned family credentials remain in their current user tables. Assigned users without a personal profile have platform-scoped `central-user-info` for their own registered information. No account identity, invitations, RSVP history, address credentials or production database is recreated.

A host's `guest`/`address` rows remain local Address Book entries. Editing them does not modify a person account, its verified contact, private link, devices or central family profile. Attempts to submit central authentication fields through a contact editor are rejected server-side. Registered-account address moves may invalidate only the local party session context, never that person's sessions at other households. Local aliases/phone/address edits remain local; legitimate shared central changes continue using the existing authoritative profile propagation. Approved contacts update without repeated approvals, keeping local notes and other private data. Existing matching, link approvals, sharing choices, Remove/Block and invite/uninvite flows are retained.

A registered adult cannot change another registered adult's central name, phone or parent association through the shared family editor, or archive that adult as an indirect edit. Shared family addresses remain family-level central information, as in the existing personal profile model. A system administrator changing that address is editing the shared family record; they are not moving guests or replacing address IDs. Own username/recovery-phone editing remains available; changing the recovery phone invalidates the previous verified security contact and old challenges rather than silently trusting the new phone.

## Restricted administrator controls

**Administrator → Hosts → Registered accounts** opens a dedicated management page using existing controls. It does not replace or redesign Address Book pages or shared toolbars. Each registry/audit query, update, private-link disclosure/reset, send request, session revocation or assigned-password recovery requires the current system-administrator password. Confirmation uses the existing password KDF and rate limits and rechecks current system permission/session state. Ordinary hosts, household administrators, regular family members and guests cannot invoke these APIs. System access is the existing platform-administrator permission, not a household role.

The registry covers users across households and shows registered names, address/phone data, email where available, household IDs and active session counts. Versioned updates reject stale personal/account records. Phone recovery requires the administrator to attest that the intended person and number ownership were verified outside the current sign-in attempt and that security-text delivery is authorized. This is not proof supplied by a host or an arbitrary claimed phone number.

For guests, a confirmed administrator phone change updates central recovery information and the verified security-contact record, revokes active guest sessions/challenges, cancels stale recovery/verification messages, and propagates permitted shared information. Future private sign-in challenges use that verified central number. Identities, relationships, household IDs, invitations and RSVP records remain unchanged. Address changes retain host-local notes and unrelated central address metadata. The registered/shared mailing address and physical address have separate controls; the existing mailing-follows-physical choice is preserved rather than being reset. Assigned family password resets move to the restricted system-administrator control; household managers may continue managing local membership/role access, but cannot reset another registered person's authentication password. Own password changes still require the current password.

Audit records are stored as `account-admin-audit` in the platform scope and can be read only through the password-confirmed system-admin endpoint. Entries contain actor, subject, action, timestamp and changed-field names, never secret URLs/IDs, OTPs, passwords, message bodies or provider diagnostics. They do not appear in host/guest projections or ordinary logs.

## Private guest links and revocation

Private sign-in links use 256-bit random IDs, URL fragments, AES-256-GCM encrypted storage with identity-bound authenticated data, and a separate lookup hash. The URL/ID can be disclosed only to the guest themself or a freshly password-confirmed system administrator. Registry/host projections never include the token or encrypted secret. Administrator disclosure fields clear on blur/visibility loss or after one minute and are never put in local storage. The fragment is removed from the address bar after the dedicated sign-in page captures it in memory.

Reset atomically replaces the secret/hash and revokes existing guest sessions/challenges. The previous URL immediately fails proof lookup, and already-issued old challenges cannot establish new sessions. Reset retains the same central identity and stored history. Administrator phone edits also invalidate stale proofs through contact-version binding. Revoke invalidates authorized session cookies; it does not delete the person/account or responses.

Hosts get only **Send private sign-in link** in their existing adult-contact editor. It sends directly to the central verified number, respects blocking/opt-out checks and returns a bounded delivery status without the URL, token or phone. A local contact edit cannot redirect this delivery. System administrators can deliver the replacement link through the restricted management control. Uncertain sends are not automatically retried.

The dedicated `/guest#…` sign-in flow requires the private link, central registered names, a current household/address ID and a single-use SMS challenge. The link alone is not authentication. OTPs are short-lived keyed hashes, bounded by persistent attempt/send limits, bound to the current link/contact/address versions, and never logged. Completing private verification activates that stronger sign-in method and revokes older guest sessions; username/name shortcuts cannot bypass it afterward. Existing sign-ins are retained for accounts not yet activated, rather than forcing a configuration-dependent global migration.

## Configuration and rollout boundary

No runtime setting, credential or live account is changed by this implementation. SMS remains disabled. Private-link creation/disclosure requires an owner-configured `GUEST_LINK_ENCRYPTION_KEY` containing 32 random bytes encoded as 64 hexadecimal characters. Supply it only through secure Worker secret settings, never chat/source/logs; preserve an existing correct key. Delivery/OTP also require the existing SMS provider configuration, `SMS_ENABLED=true`, and a verified central contact. This task does not activate SMS or authorize changing provider credentials. With missing configuration, these operations fail closed before sending or leaving queued messages. Existing ordinary account management remains usable.

No live test account, SMS, data reset or reverse migration is used. Node/API and phone/desktop tests run with isolated databases and synthetic identities. The only enabled-provider tests inject a mock transport and assert the destination, token secrecy, replay protection and session revocation. Real sign-in/delivery acceptance remains unverified until separately authorized provider configuration and an existing authorized account are available.

Public changes are limited to these account/security controls and use the existing styles; CSS and existing Address Book structure are unchanged. The appearance manifest is updated so the owner can review the exact UI additions. Apply the existing `approved-appearance-change` owner label to the review PR before merging; production release guards and the manual recovery workflow are unchanged apart from adding regression tests to the existing browser matrix.

## Completed non-production validation

Validation passed for the existing application plus the new permission/security cases: 148 API tests, all 12 browser suites (with additional final focused runs for account and family controls), 2 Cloudflare runtime checks including encrypted private-link reset against real local Durable Object storage, 22 release/metadata safeguard tests, 6 unchanged AnyList adapter tests, formatting and the local events Worker dry-run bundle. Security regressions cover role denial, local-contact isolation, registered-adult ownership, current-password confirmation, central phone/address synchronization, URL invalidation, challenge replay/session revocation, assigned-account recovery, unchanged invitation/RSVP data, preserved household IDs/notes, and cross-household session isolation during a local address move.

No production website or account was tested or changed. The only enabled-SMS test uses an injected fake transport. Live provider delivery and existing-account acceptance remain unverified. The branch is for owner PR review/merge; Codex does not create a PR or deploy it.
