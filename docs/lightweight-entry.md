# Lightweight browser entry and secure transfers

PR #108 cut the browser module waterfall and removed full application downloads
from intermediate sign-in transfers. Gather still made separate setup, configuration,
household context, interface, session, and host reads. Several of those requests
each independently checked the same Firebase account.

## Normal Home and event entry

`client/app.js` is the original shared application source. Shared modules remain
in `public/`. `npm run build:browser` uses the already pinned esbuild dependency to
produce one deterministic `public/app.js`. It preserves the original URL, same
renderer, styles, event content, toolbars, Google/Firebase imports and API behavior.
The only static external import is `/auth-bootstrap.js`: authentication fragments
must be captured exactly once in that shared module's memory.

Before this change, a cold page fetched 26 JavaScript modules (547,287 source
bytes). It now fetches two entry files (414,746 bytes). This matters in production:
these requests traverse the household gateway/Worker and authoritative database
routing checks. Preloading alone still incurred all of those requests. No routing
cache, authorization shortcut, gateway change or database change is introduced.

Home declares its data request in the document so the browser can start it
while fetching both JavaScript entries. Transfer documents wait for any
browser-bound redemption before starting their data request. Home uses
`GET /api/startup?view=home` for setup status, public interface configuration
and the current session. Once authorized, a replacement-mode host receives the
household and its event views. Contact and address records, roster data, saved
menus, and editing templates are read on demand through `/api/host/workspace`.
Concurrent requests for the same in-memory Home snapshot share one read.
Navigation can reuse that data until a new snapshot replaces it. Family
Workspace keeps its own data when returning to Home within a validated session.
Refresh and account changes invalidate inactive data. Existing consumers of
`/api/startup` and `/api/host` can still request the full projection.

These responses are no-store and apply the existing origin, session renewal,
provider revocation, and household role checks. The startup response reports
`auth` and `snapshot` durations through `Server-Timing` where supported by the
runtime. This excludes edge transit and browser work. A fresh load or protected
operation still validates its session on the server.

Direct public event links send the shared event introduction and allowlisted
public snapshot with the HTML. Visitors can read the title, description, date
and location while the JavaScript downloads. The application reuses that
snapshot for its first render. In host-only mode legacy invitation links take
the same path and update the address in the current document. Individual
private-page grants are checked separately after the public event and RSVP
control render. The first response never contains private page content. Ordinary
Firebase email/Google sign-in uses the fresh SDK sign-in token, which Gather
still verifies against Firebase and the approved host mapping. Email verification
completion refreshes the identity before submitting it.

## Cross-domain authentication

`/signin` serves the existing shell with only the small credential-capture entry.
The transfer entry is 4,865 bytes; it does not fetch the application on the
intermediate prepare/authorize pages or a verified Google callback.

It calls the **existing** browser-bound, single-use handoff API, follows only
server-generated transfer destinations, and imports the app after redemption.
An expired source session falls back to the same shared sign-in UI with its request
held only in module memory. Administrators and hosts still use one sign-in form;
Meyer's existing password/admin authorization and ordinary host Firebase remain
unchanged. A household ID still authorizes only an invitation RSVP, not sign-in.

Secure cross-origin navigation remains necessary; it is not replaced with shared
Domain cookies, exposed credentials, hidden guest accounts or client-side trust.
The change avoids loading the entire UI at each hop. The browser regression uses
synthetic HTTPS origins and the real shared API: all three prepare/authorize/redeem
calls remain, while the app is requested **once on the final household**. A verified
OAuth callback similarly reaches its household without loading the app in between.
Refresh of an already signed-in household performs no additional handoff.

## Reproducible build and release safety

Run `npm run build:browser` after modifying `client/` or shared UI modules. Never
edit the generated `public/app.js` or `public/auth-bootstrap.js` directly. All test
commands compare generated bytes to the reviewed sources. The build also refuses
a large transfer entry or new static dependency waterfalls. The release manifest
includes both generated assets; normal byte/provenance checks remain mandatory.
Untracked `client/` files are rejected by committed-source validation.

Keep the source files, generated entries and updated manifest in the same commit.
No runtime build service, new dependencies, new asset host or production flags
are required. The existing manual recovery workflow and database lineage remain
unchanged. Existing clients still have all original module URLs available.

## Verification boundary

Regression coverage checks cold Home/event entry, actual shared full-page RSVP,
Google/email/Firebase compatibility, secure multi-origin native handoffs, expired
source fallback, malformed tokens/redirect envelopes, and approved design pixels.
It counts requests and application downloads rather than asserting that changing
the loading message fixes latency. All fixtures and provider responses are local
and synthetic; no real accounts or invitation responses are modified.

Run `node --test test/startup-mobile.js` for browser diagnostics. The startup
test reports milliseconds to first usable UI, Gather API requests, authoritative
Firebase session lookups, initial loading-screen displays, and document loads.
It applies fixed synthetic transport delays and mocks external providers while
exercising the real shared server. Its timings characterize local browser
behavior and do not represent production page timings.
