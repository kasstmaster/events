# Security boundaries and release prerequisites

This is a new application in `kasstmaster/events`. It does not read, migrate, write to or deploy the existing Meyers Gatherings site or its private data repository. The reference informed adult-level RSVPs, child association, declined attendance, menu claims and deadline behavior; its codebase was not copied.

## Trust boundaries

- Administrators approve host email addresses and manage shared templates and scoped public-page defaults. Read-only guest previews exclude private contacts, notes and responses; the deletion summary returns scoped counts and confirmation identifiers, not guest databases. Browser administrator setup requires an owner-configured `ADMIN_SETUP_TOKEN` secret, never a default password or public first-user ownership claim. The optional bootstrap CLI remains available to operators.
- Hosts own one household each, with reusable guests, addresses and independent events. Record access includes both the record ID and the authenticated household. A record ID from another tenant produces no usable private data.
- Guests receive only events inviting their adult ID, the invited children associated with that adult, their own response/claims, aggregate attendance counts and menu availability. Other names, household addresses and RSVP details are excluded.
- Public household links return only household ID/slug, display name and login design. Treat those branding settings as public. A stable QR is a navigation link, not an authentication credential.
- Images are administrator/host-provided raster data URLs. They are not uploaded to a third party. Registry URLs are external navigation only; the server never fetches them. Registry links open with `noopener noreferrer`.
- Cookies, password hashes and sessions never appear in client API payloads or application logs. Request failures log only an error type/code, not request bodies. SQLite files and their containing directory must remain private.

Names alone cannot distinguish the real invitee from someone who knows that name. Rate limits and data minimization reduce exposure; they cannot provide identity assurance. Exact same-name/suffix duplicates fail closed rather than selecting an arbitrary account. Hosts must correct ambiguous records with the actual guest; the application never offers a list of matching private accounts or invents identifying suffixes. Children cannot authenticate independently.

## Synchronization and consistency

SQLite transactions protect centralized state: Node uses WAL, while Cloudflare uses SQLite-backed Durable Object storage and synchronous native transactions. Large records use transactional ordered chunks; indexed lookup metadata stays in the main row. Host mutations use optimistic versions. Guest capacity is calculated from current committed responses inside an immediate transaction, with per-adult RSVP versions. Data persists without live browser sessions and reads are never backed by local storage. Polling has a 10-second latency and pauses during editing; offline writes are not queued or replayed.

The server uses UTC calendar dates for deadline enforcement. Menu quantity increases after the deadline are disallowed while attendance changes and claim reductions remain available. Existing over-capacity claims are intentionally retained if the host lowers a menu target.

## Before any approved Internet deployment

1. Follow [Cloudflare deployment](cloudflare.md) for the selected Worker/SQLite-backed Durable Object setup, or for a separately approved Node server choose a domain, server and private durable database volume; set the exact HTTPS `APP_ORIGIN`, `NODE_ENV=production` and listener settings. Terminate TLS at a trusted edge and keep the database, bootstrap environment and filesystem backups private. The server sets Secure cookies and HSTS for HTTPS origins.
2. Use a supported Node.js 24 release and `npm ci` from the committed lockfile. Run both automated suites. No source rewrite or frontend secret injection is needed.
3. Provide a real administrator password securely; clear bootstrap variables after use. No email provider, verification service or automated mail workflow exists.
4. Configure access and rate limits at the trusted edge. The generic Node adapter uses the TCP peer address and intentionally ignores forwarded IP headers. The Cloudflare adapter uses the platform-provided `CF-Connecting-IP` and overwrites its private forwarding header at the edge. All clients behind one reverse proxy currently share its application-level IP limit (30 attempts per operation per 15 minutes); email/name-specific limits are separate (10). Do not blindly trust arbitrary `X-Forwarded-For`. Multi-replica or high-volume operation needs a reviewed trusted-proxy/rate-limit strategy.
5. Establish consistent SQLite backups and a tested restoration process. Use one writable server/database instance; do not give replicas independent database copies. Stored images make backups larger; consider an authorized tenant-scoped object store for larger installations.
6. Accept the documented name-only guest identity limitation or approve a stronger guest credential model before storing information requiring stronger assurance. The present application does not include host MFA, password recovery, account disabling, or a security audit trail. Do not claim those capabilities exist.

These are documented deployment prerequisites, not an authorization to deploy. A saved configuration, build or local validation does not prove deployment. Deployment requires working access to the specifically selected Cloudflare account; do not touch the gatherings site. The `/setup` page is publicly reachable, but administrator creation requires a constant-time checked, owner-configured token of at least 32 characters and the exact application Origin. Attempts are persistently rate-limited. The password is scrypt-hashed server-side; no setup credentials are logged, returned, put in URLs or stored in browser storage. A transactional recheck and persistent completion marker enforce single-use setup, including across runtime restarts and concurrent submissions. Existing administrators close setup immediately. Delete the setup token after successful login. The legacy scrypt-hash bootstrap remains compatible and never overwrites an existing administrator.

## Household hostname boundaries

See [household subdomain security and rollout](household-subdomains.md). A validated hostname selects household data only after the events edge verifies a short-lived HMAC from the exact allowlisted gateway. The client cannot authenticate by setting a forwarding or household header. The gateway has one exact upstream and rejects redirects; mutation nonces prevent replay. Custom-host sessions are origin-bound and use host-only `__Host-events_session` Secure/HttpOnly/SameSite=Strict cookies. CSRF checks retain the browser's actual Origin and reject sibling household origins. Admin setup and registration remain canonical-only. Guest invitation checks and host tenant scoping remain server enforced. Reserved/retired names cannot be taken over; addresses are derived from the registration household name and cannot be changed by hosts, including through API calls. Display-name edits preserve their original claim; legacy retired labels remain unavailable. No DNS API access is exposed to hosts, no live synthetic fixtures are created, and no data is migrated.

Registration availability is a rate-limited advisory read, not a reservation or authentication check. The server recomputes the normalized whole-name label in the approval/household/user/claim transaction. Failed claims leave approval untouched. The browser preview cannot override the server-selected label. Empty, short, reserved, retired or conflicting names are rejected; no numeric alternative is generated. The approved runtime setup grants only the events backend a narrowly scoped domain-account token; no frontend/host/API response contains it. A durable transactional outbox in the same database drives exact-host provisioning with POST-only conflict checks, private anonymous GET probes, bounded retries and activation after verified DNS/TLS/gateway traversal. A pending probe cannot invoke private/session/mutation APIs. The uncached signed gateway status lookup and app both check the authoritative claim. See the rollout guide for required permissions and fail-closed rollback. The owner-approved runtime credential and automatic service are deployed. A failed live verification remains pending; source publication or a successful build alone does not authorize activation.

The provisioning verifier stores only fixed verification stage/failure codes (and numeric HTTP status), not transport exception text, URLs, request/response headers, body content, credentials or private probes. Both Worker configurations must retain `global_fetch_strictly_public` for the public Worker routing architecture. A configuration regression must not be hidden by separately hardcoded test-runtime flags; local network mocks still do not establish live cross-account success.

Signed private status/context verification reads may emit fixed `events-routing-check` stage/outcome codes and numeric HTTP status for temporary real-time diagnosis. The reporter rejects unknown/free-form values, and never logs hostname, household, probe, headers, cookies, bodies or exception values. Tracing must not enable access or change pending/active state.

## Editing, messaging and deletion boundaries

See [shared feature security and operations](shared-editors.md). Edited interface wording is escaped text; layouts use a server-validated key schema. Template fields are allowlisted and escaped, and saved cards snapshot designs rather than tracking source updates. Notes and reminder configuration are never serialized by public or guest endpoints.

SMS provider credentials stay server-side and delivery is disabled by default. Signed provider webhooks are the only browser-Origin exception and must pass Twilio signature verification on the exact canonical URL. Global opt-out suppressions and unique delivery claims prevent repeat attempts; uncertain outcomes remain unknown. Tenant deletion immediately revokes access, retains retired labels and only cleans exact resources verified against ownership receipts. Pending cleanup must not be bypassed by rollback. No provider setup, live messages or real account deletions occur in automated validation.
