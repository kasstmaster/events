# Security boundaries and release prerequisites

This is a new application in `kasstmaster/events`. It does not read, migrate, write to or deploy the existing Meyers Gatherings site or its private data repository. The reference informed adult-level RSVPs, child association, declined attendance, menu claims and deadline behavior; its codebase was not copied.

## Trust boundaries

- Administrators approve host email addresses and manage shared templates and platform page defaults only. They cannot edit individual households or events. Only administrators can edit interface wording/layout; hosts can edit their own content and scoped formatting. Read-only guest previews exclude private contacts, notes and responses; the deletion summary returns scoped counts and confirmation identifiers, not guest databases. Browser administrator setup requires an owner-configured `ADMIN_SETUP_TOKEN` secret, never a default password or public first-user ownership claim. The optional bootstrap CLI remains available to operators.
- Hosts own one household each, with reusable guests, addresses and independent events. Record access includes both the record ID and the authenticated household. A record ID from another tenant produces no usable private data.
- Guests receive only events inviting their adult ID, the invited children associated with that adult, their address group’s permitted attendance answers and their own claims, aggregate attendance counts and menu availability. Other names, household addresses and RSVP details are excluded.
- Public household links return only household ID/slug, display name and login design. Treat those branding settings as public. A stable QR is a navigation link, not an authentication credential.
- Images are administrator/host-provided raster data URLs. They are not uploaded to a third party. Registry URLs are external navigation only; the server never fetches them. Registry links open with `noopener noreferrer`.
- Cookies, password hashes and sessions never appear in client API payloads or application logs. Request failures log only an error type/code, not request bodies. SQLite files and their containing directory must remain private.

Guest authentication requires matching adult names and a four-digit address code, shared by guests explicitly assigned to one household-scoped address record. A shared code proves address-group access, not individual identity; residents who know another resident’s name can act for that person. Maintain IP/name attempt limits and generic recognition errors. Identical first/last/suffix names within one group fail closed unless they are explicitly linked to the same identity. Children never sign in independently. Codes have 10,000 possible values, are assigned without replacement and retained after retirement; exhaustion stops new groups rather than reusing credentials. No-address guests receive separate fallback codes. Address text edits preserve the code; moving a guest changes its credential and revokes existing identity sessions. Legacy individual aliases survive only until that guest moves, and are never copied to linked entries in another household.

Guest event payloads may include explicitly invited adults/children sharing the authenticated entry’s address and their attendance answers, with separate response versions. They exclude other-address guests, their responses, contacts, phone numbers and notes. Address-wide RSVP commits are atomic; blank/omitted people remain unchanged, including claims/custom items, and stale affected responses reject the whole mutation. Event invitations and designated-adult rules still apply. Cross-host linking remains explicit and guest-approved; a host sees only its own address code. Undo restores identity membership without changing address credentials. Removed hosts do not invalidate other hosts’ guest identities or current address codes.

## Synchronization and consistency

SQLite transactions protect centralized state: Node uses WAL, while Cloudflare uses SQLite-backed Durable Object storage and synchronous native transactions. Large records use transactional ordered chunks; indexed lookup metadata stays in the main row. Host mutations use optimistic versions. Guest capacity is calculated from current committed responses inside an immediate transaction, with per-adult RSVP versions. Data persists without live browser sessions and reads are never backed by local storage. Polling has a 10-second latency and pauses during editing; offline writes are not queued or replayed.

The server uses UTC calendar dates for deadline enforcement. Every guest RSVP mutation after the deadline is disallowed, including attendance changes and claim reductions. Existing over-capacity claims are intentionally retained if the host lowers a menu target.

## Before any approved Internet deployment

1. Follow [Cloudflare deployment](cloudflare.md) for the selected Worker/SQLite-backed Durable Object setup, or for a separately approved Node server choose a domain, server and private durable database volume; set the exact HTTPS `APP_ORIGIN`, `NODE_ENV=production` and listener settings. Terminate TLS at a trusted edge and keep the database, bootstrap environment and filesystem backups private. The server sets Secure cookies and HSTS for HTTPS origins.
2. Use a supported Node.js 24 release and `npm ci` from the committed lockfile. Run both automated suites. No source rewrite or frontend secret injection is needed.
3. Provide a real administrator password securely; clear bootstrap variables after use. No email provider, verification service or automated mail workflow exists.
4. Configure access and rate limits at the trusted edge. The generic Node adapter uses the TCP peer address and intentionally ignores forwarded IP headers. The Cloudflare adapter uses the platform-provided `CF-Connecting-IP` and overwrites its private forwarding header at the edge. All clients behind one reverse proxy currently share its application-level IP limit (30 attempts per operation per 15 minutes); email/name-specific limits are separate (10). Do not blindly trust arbitrary `X-Forwarded-For`. Multi-replica or high-volume operation needs a reviewed trusted-proxy/rate-limit strategy.
5. Establish consistent SQLite backups and a tested restoration process. Use one writable server/database instance; do not give replicas independent database copies. Stored images make backups larger; consider an authorized tenant-scoped object store for larger installations.
6. Privately distribute mandatory guest codes before rollout. Existing name-only guest sessions are invalidated; no invitation, response or link is deleted. Household members have password-confirmed ownership transfer, recovery and immediate session revocation on password/disable/remove changes. Platform-assisted current-owner recovery requires administrator password and exact registered host-email confirmation. MFA and a comprehensive audit trail are not implemented.

These are documented deployment prerequisites, not an authorization to deploy. A saved configuration, build or local validation does not prove deployment. Deployment requires working access to the specifically selected Cloudflare account; do not touch the gatherings site. The `/setup` page is publicly reachable, but administrator creation requires a constant-time checked, owner-configured token of at least 32 characters and the exact application Origin. Attempts are persistently rate-limited. The password is scrypt-hashed server-side; no setup credentials are logged, returned, put in URLs or stored in browser storage. A transactional recheck and persistent completion marker enforce single-use setup, including across runtime restarts and concurrent submissions. Existing administrators close setup immediately. Delete the setup token after successful login. The legacy scrypt-hash bootstrap remains compatible and never overwrites an existing administrator.

## Household hostname boundaries

See [household subdomain security and rollout](household-subdomains.md). A validated hostname selects household data only after the events edge verifies a short-lived HMAC from the exact allowlisted gateway. The client cannot authenticate by setting a forwarding or household header. The gateway has one exact upstream and rejects redirects; mutation nonces prevent replay. Custom-host sessions are origin-bound and use host-only `__Host-events_session` Secure/HttpOnly/SameSite=Strict cookies. CSRF checks retain the browser's actual Origin and reject sibling household origins. Admin setup and registration remain canonical-only. Guest invitation checks and host tenant scoping remain server enforced. Reserved/retired names cannot be taken over; addresses are derived from the registration household name and cannot be changed by hosts, including through API calls. Display-name edits preserve their original claim; legacy retired labels remain unavailable. No DNS API access is exposed to hosts, no live synthetic fixtures are created, and no data is migrated.

Registration availability is a rate-limited advisory read, not a reservation or authentication check. The server recomputes the normalized whole-name label in the approval/household/user/claim transaction. Failed claims leave approval untouched. The browser preview cannot override the server-selected label. Empty, short, reserved, retired or conflicting names are rejected; no numeric alternative is generated. The approved runtime setup grants only the events backend a narrowly scoped domain-account token; no frontend/host/API response contains it. A durable transactional outbox in the same database drives exact-host provisioning with POST-only conflict checks, private anonymous GET probes, bounded retries and activation after verified DNS/TLS/gateway traversal. A pending probe cannot invoke private/session/mutation APIs. The uncached signed gateway status lookup and app both check the authoritative claim. See the rollout guide for required permissions and fail-closed rollback. The owner-approved runtime credential and automatic service are deployed. A failed live verification remains pending; source publication or a successful build alone does not authorize activation.

The provisioning verifier stores only fixed verification stage/failure codes (and numeric HTTP status), not transport exception text, URLs, request/response headers, body content, credentials or private probes. Both Worker configurations must retain `global_fetch_strictly_public` for the public Worker routing architecture. A configuration regression must not be hidden by separately hardcoded test-runtime flags; local network mocks still do not establish live cross-account success.

Signed private status/context verification reads may emit fixed `events-routing-check` stage/outcome codes and numeric HTTP status for temporary real-time diagnosis. The reporter rejects unknown/free-form values, and never logs hostname, household, probe, headers, cookies, bodies or exception values. Tracing must not enable access or change pending/active state.

## Editing, messaging and deletion boundaries

See [shared feature security and operations](shared-editors.md). Edited interface wording is escaped text; layouts use a server-validated key schema. Template fields are allowlisted and escaped, and saved cards snapshot designs rather than tracking source updates. Notes and reminder configuration are never serialized by public or guest endpoints.

SMS provider credentials stay server-side and delivery is disabled by default. Signed provider webhooks are the only browser-Origin exception and must pass Twilio signature verification on the exact canonical URL. Global opt-out suppressions and unique delivery claims prevent repeat attempts; uncertain outcomes remain unknown. Tenant deletion immediately revokes access, retains retired labels and only cleans exact resources verified against ownership receipts. Pending cleanup must not be bypassed by rollback. No provider setup, live messages or real account deletions occur in automated validation.

## Family authorization and imported content

Household owners/administrators are not platform administrators. Regular members cannot manage accounts or child permissions. Kids see only specifically permitted records within specifically permitted folders, plus their assigned chores. Every feed, direct request, search, download and notification uses the same server predicate. Revocation takes effect on the next request/poll; previously downloaded bytes cannot be recalled. Role/ownership/password changes revoke sessions. Shared host contacts and notes never enter public/family-member/guest responses.

Private files are authenticated attachments from chunked SQLite records, with per-file and household limits and content-type/signature validation; no public object storage is used. Unsupported legacy recipe records remain stored but are excluded from authorized reads, search and edits; their importer and endpoints have been removed. In-app notifications are scoped, deduplicated and permission checked at delivery/read; no external channel is enabled.

The address-code card variable is optional. Only a host-owned recipient and an explicitly present `recipient.inviteCode` element permit the server to snapshot that code into a private card context. Shared templates contain the variable definition only; public/guest data and ordinary card contexts do not contain the code. Preview selection outlines, resize handles and snap guides never enter exported SVG/PNG/print content.

Default-page examples are built synchronously from browser-only synthetic state using the live renderer/layout functions and restored before callbacks run. A scriptless, form-disabled sandbox frame isolates the example; parent-controlled edits affect only the draft defaults. Interface text is editable as plain text and escaped on rendering. Host-owned sample values cannot become wording overrides. Card editing is a full-page shared editor with polling paused until it closes.

Page appearance is normalized per inheritance layer into five shared categories; legacy aliases cannot bypass category mapping. Appearance saves remain tenant-scoped/versioned and omit resolved administrator-only wording/layout configuration. Global appearance changes retain existing household/event resolved styles transactionally. Inline guest drafts are browser-only until validated atomic Save, pause polling and retain all existing address/identity/child/version checks. Address grouping uses IDs rather than titles and grants no access. Administrator management screens are dedicated/inline; destructive confirmation and read-only preview protections remain. The administrator password endpoint requires the current password, hashes the new password and revokes all existing administrator sessions. See [toolbar editing](fixed-toolbars-inline-editing.md).

Bulk invitations from Contacts are additive and host-only, with exact-origin protection, session-derived ownership and required event versions. The event-edit and bulk endpoints share invitation/child validation. The invitation union is transactional; no existing RSVP, claim, contact credential, event content or unrelated field is rewritten, and rejected/stale/mixed-tenant selections do not partially commit. This changes event access only and does not send messages. Browser selections remain transient until the user chooses an event.

## Optional contacts import and RSVP confirmations

See [Meyer AnyList](meyer-anylist.md). Enable the integration by a private operator-selected existing verified host email, optionally also its exact household ID. The browser cannot select the target. All other roles/households are denied server-side. The canonical-origin callback uses a separate constant-time checked secret and a bounded expiring job; no ordinary host session can import. Imports transact against a contact/address revision and preserve source mappings, distinct people, invitations, responses, private fields, local moves and STOP state. Dispatch uses Cloudflare-native manual redirect handling and rejects redirects without forwarding the credential. The reader only reads AnyList, never touches Gatherings/state repositories, emits no personal provider diagnostics and caches no credentials. Never expose imported data as a workflow artifact or browser-wide defaults example. The Worker accepts Gatherings-style `GITHUB_TOKEN` (preferred) or legacy `EVENTS_ACTIONS_TOKEN`, but dispatch remains restricted to the Events workflow on main. Optional workflow repository/branch settings fail closed for other destinations. Token-format failures and HTTP dispatch outcomes produce fixed actionable messages without provider bodies or exception text. Saved credentials are not automatically shared between Workers or repositories. Live activation requires Events-specific secure settings; source publication alone does not connect an account.

The contact form no longer asks a host to assert SMS consent. Only a successful explicit attendance answer for the signed-in adult records phone-scoped RSVP enrollment and a single event confirmation; another resident's or child's answer cannot enroll that person. Enrollment is a separate private record so it does not invalidate an unsaved host contact editor. Enforce STOP globally, current phone/adult/invitation/response and nondeleted household immediately before the one-shot send. Expire queued confirmations after 24 hours. Provider-disabled submissions remain disabled permanently; uncertain attempts are never retried. Notifications use the same existing private delivery table and shared transport as reminders, with fixed errors and no raw provider response logging. Enabling provider credentials/SMS remains a separate operator action; this change sends no live messages and introduces no new cron or binding.

Host and guest event bodies share one renderer without host instructions or private notes. The host RSVP control opens a read-only explanation and has no guest submission path. Double-click editing binds only to host-owned values; shared wording/layout remain platform-admin-only. Table templates are scoped to the authenticated host household, validate with the shared event-menu schema, require versions for updates/deletions and snapshot only menu fields. Applying them appends fresh item IDs to a browser draft; saving templates cannot update existing events or claims. Guest/family/admin sessions cannot use template endpoints. Existing RSVP/claim checks remain authoritative when an event draft is eventually saved.

## Host accounts with platform administrator tools

A separate `platform-access` record grants platform administration to an existing registered host user ID/email. It never changes `users.role`, ownership, passwords, household design or content. Sessions advertise a boolean capability and server-side administrator checks consult the current record. Host/family management authorization stays separate; changing a display name, hostname, client role or household settings cannot grant platform access. Disabled/deleting or removed host accounts cannot use the capability. Only a current platform administrator can grant it, after confirming their own password and the exact registered target email. The UI adds Approvals, Hosts, Defaults and Templates in that host's Home top toolbar, retaining normal host bottom navigation and event appearance. Global defaults still affect platform defaults only; private household editing is not added to administrator management.

Retiring an old administrator requires a password-confirmed promoted host and a fresh successful host sign-in after promotion. The server deletes only the exact confirmed legacy `role=admin` login, revokes its sessions and writes the permanent setup-completed marker in the same transaction. A legacy administrator cannot delete itself through this route; the remaining host account and all household data are retained. Do not retire the live old account until the promoted host's real administrator access has been verified. Synthetic tests verify the handoff; a source change or test account is not a live permission change.

Host guest previews are scoped to the authenticated household. Identifiers cannot select another household; preview responses strip private notes, invitations, phones, access codes and real guest/response data and perform no writes. Platform administrators retain explicit administrator preview across households. Three-dot menu previews never submit RSVPs. Guest event choices use the shared renderer with upcoming dates ascending, undated events after upcoming ones and most recent past dates before older past dates; the server remains authoritative for invitation visibility.

The home-card/options-menu follow-up removes all dedicated notes entry/display surfaces without deleting legacy private notes or weakening payload privacy. Event/contact requests omit removed note fields so existing server fallback preserves them; family record drafts retain unexposed note/history values. Shared navigation adds no access: only hosts receive Contacts/Family Home cards and edit/share options; other roles keep their authorized menu actions. Account recovery, administrator tools, preview restrictions and confirmation dialogs remain unchanged.

Host bulk uninviting uses the same invitation/RSVP validator as event editing. It requires the authenticated household and exact current event version, validates selected contact ownership, and atomically removes only the chosen contacts from that event. Saved adult or child attendance answers reject removal of the whole batch. No responses, claims, contact IDs, address codes or other events are changed, and no messaging is queued. Confirmation is a user safeguard; server authorization and version/RSVP validation apply even when the endpoint is invoked directly.

## Host-entered RSVPs and address notes

Authenticated hosts may read/write RSVP projections only for explicitly invited contacts in their own household via `/api/host/events/:eventId/rsvp/:guestId`. Child selections resolve to their designated invited adult. These writes reuse atomic address-party response versions, skip preservation, attendance/claims validation and capacity checks. Only this server-authorized path may bypass the guest deadline. Manual host answers never establish guest messaging consent or queue SMS confirmations. Guest endpoints cannot opt into these privileges through request flags; guest experience preview stays read-only.

Saved address notes are private to the owning host and returned only with scoped host contacts and RSVP dashboards. Versioned address writes retain notes on omitted fields, and AnyList updates preserve them. Never include notes in public, guest, preview, family or card projections. Container images accept only bounded uploaded raster data through the existing image validator; no external image URLs or SVG uploads are allowed.
