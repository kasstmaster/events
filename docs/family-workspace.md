# Family workspace and shared guest identities

## Guest identity rollout

This owner-approved product change replaces name-only sign-in with first name, last name and a permanent random invite code. Existing opaque household URLs, QR destinations, guest IDs, invitations, responses and menu claims stay intact. Existing name-only guest sessions fail closed and must sign in again. Original hosts obtain their existing guests’ codes from the private Address book and share them privately; the application sends no messages. Codes are generated lazily for old guest records and remain stable on edits. Suffix recognition requires the code and matching names, and returns only whether a suffix is required.

Address-book add/edit performs normalized server-side matching (names, punctuation/suffixes and weighted addresses/abbreviations). No automatic merging occurs. Candidate evidence is only name and household with an expiring ticket. Use Existing requests a connection; it does not itself grant access. The existing guest signs in with their permanent code and approves pending requests. Until approval, the new entry retains its separate code. Create Separate preserves an independent identity. A child’s connection requires their designated adult to be connected first. Cross-host sign-in shows only explicitly invited relationships and each inviting household’s branding; entry-domain login branding and host-only origin-bound cookies stay intact.

Each host retains their own contact fields, addresses, private notes, children and invitations. Linking never copies them. Hosts cannot obtain another host’s code/contact records. Confirmed undo of a linked entry restores its previous identity/code, retains all local records/responses, closes pending requests and revokes affected identity sessions. The original/source entry is not an undo target. Global identities/codes are reserved permanently, including after guest/host removal; another host’s invitations survive. If the originating host is removed before linking, an adult can connect a new entry using both the new entry’s code and their old permanent code. No name-only recovery or code reassignment is allowed.

## Accounts and permissions

The existing host becomes owner without replacing their sign-in. Owners create household administrator, regular member and kid accounts with household-scoped login names/passwords; children need no email. Household administrators can manage ordinary members and child access but cannot appoint administrators, remove the owner or transfer ownership. Only the owner controls those operations. Regular members use shared adult content, lists, recipes, records and adult chores. Kids add/check items on permitted lists and complete assigned chores; they cannot manage permissions, accounts or destructive actions. These roles never imply platform administration.

Owners/managers can reset eligible member passwords, disable or remove members; removal is a retained disabled record to preserve task history and prevent login reuse. Password changes require the current password; transfer requires the current owner’s password and revokes household sessions. The new owner can remove the former owner. Platform-assisted current-owner recovery requires the platform administrator’s password and exact registered host email. No automatic emails or password-sharing flows exist.

Child access defaults empty. An owner/administrator selects individual children on each record and folder; a child must be allowed on both the target and every enclosing folder. A parent grant never exposes all descendants. The same predicate controls direct reads, search, polling, private file downloads and notifications. Assigned chores are the sole exception: the child sees their assignment, while a restricted linked record/title remains hidden. Revocation stops subsequent requests and reminders; it cannot recall downloaded files.

## Workspace behavior

- Lists have user-created folders/categories, manual category ordering and uncategorized items. Items have independent versions, checkbox and double-click/tap completion, accessible move controls/dragging, alphabetical sorting within categories and a return to manual order. Hide Completed is per member. Completed items remain until an adult deliberately deletes them. Move items before removing/renaming their category.
- Authorized pages poll every three seconds and reconnect after failure. Editors/drafts pause background replacement. A save is successful only after server acknowledgment; stale writes return 409 and retain the draft. Refresh household explicitly loads current state. Independent additions survive concurrent writes.
- Recipes support manual title, ingredients, instructions, source and notes, folders/categories/search and reviewed import from public HTTPS JSON-LD Recipe data. Unsupported sites explain manual fallback. Imports use no page scripts, cookies or credentials; every redirect is checked, at most three redirects and 1 MB content are accepted. Node resolves/pins public addresses and refuses proxied environments; Cloudflare uses the existing strict-public fetch runtime. No private-network bypass is allowed.
- Home records include serial/model, relevant dates, custom key/value details, maintenance history, notes and authenticated documents. PDF, PNG, JPEG, WebP and UTF-8 text attachments use existing chunked SQLite storage: 2 MB/file and 20 MB/household, shown in the UI. No paid service or public document URL is introduced.
- Chores have optional schedules, household IANA timezone, daily/weekly/monthly/interval recurrence, assignees, optional linked maintenance record and shared or per-assignee completion. Occurrences/history are retained separately; schedule changes cancel obsolete occurrences without erasing history. Month-end recurrences clamp to the month’s last day while retaining the anchor. Nonexistent/ambiguous daylight-saving local times are skipped. Generation is bounded to 100 occurrences per batch with a persisted cursor, a seven-day horizon and the next future occurrence. History is paginated.
- Reminders are in-app only. Quiet hours/preferences are per member (managed by adults for kids). Delivery rechecks current assignment, permissions, schedule, cancellation and completion and uses a unique chore/occurrence/member key. Existing EventsDatabase alarms and cron perform work; no extra cron, provider, browser push, email or SMS is enabled.

Family logos belong to household settings and are used in event choosers; event artwork remains separate. Hosts can enable custom RSVP items and optionally retain their names for future menus. Guest menus appear only in the RSVP dialog. Every guest RSVP edit closes after the UTC calendar deadline, retaining saved responses and claims.

## Release and recovery

Use the reviewed application merge on `feat/household-subdomains`, not the older application tree on `main`. Main carries the separately pinned manual deployment workflow. Keep SMS, automatic production builds and previews disabled. Deploy only existing `events` with `npm ci` then `npx wrangler deploy --name events --config wrangler.jsonc`. Keep account, namespace, class, object name, secrets, variables, routes and cron unchanged; do not deploy the gateway.

Record the current Worker version, closed setup status, settings/binding fingerprints and Durable Object PITR recovery checkpoint before deployment. Migrations are additive tables/indexes and record fields; existing content/responses are not rewritten. Forward-fix authorization issues rather than blindly returning to pre-family code: old code would ignore new membership rules and permit legacy name-only guest sign-in. Preserve identity/link/history/member/owner tables and retired codes on recovery. A storage restore is a last resort requiring explicit assessment of responses since the checkpoint.

Run all application, four browser suites, actual Worker/SQLite tests, formatting and both Worker dry-run bundles before merge. Synthetic fixtures only. After release verify closed setup, existing household links/QR, host/family/guest sign-in, code-qualified multi-host invitations, strict RSVP, child access and representative editor/card preview/export without fake live accounts, live messages or deletion. If deployment authentication is blocked, report the exact failed operation and the existing secure remote workflow action; never request pasted credentials or installation on the owner’s Mac.
