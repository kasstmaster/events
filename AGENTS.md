# Permanent development rules

These instructions apply to every change in this repository.

1. **Repository boundary.** Modify only `kasstmaster/events`. Other repositories, including `kasstmaster/themeyersgatherings` and `kasstmaster/themeyersevents-data`, are strictly read-only references. Never change their files, branches, settings, workflows, data or deployments.
2. **One shared application.** All hosts, households and events use the same server, components, event builder/page, guest sign-in, RSVP flow and design system. Extend existing shared functions; never create host-specific or event-specific implementations. Features and fixes must benefit everyone without overwriting individual content or settings.
3. **Customization is data.** Persist names, event content, images, invitations, menus, invitation-template choices and ordered optional registries as household/event records. Resolve design as platform defaults → household settings → event overrides. Household guest login uses household settings only. New events inherit household settings; preserve existing event formatting transactionally when household formatting changes. Editing an event must not alter household defaults or sibling events. Registry buttons belong directly below the guest RSVP button; omit the section when empty.
4. **Enforce authorization on the server.** Keep administrator, host and guest roles separate. Scope every private read/write to the authenticated household. Guests see only their invited events, their own party/response/items and permitted aggregate totals. Never expose other guests, addresses or responses through guest/public endpoints. UI visibility is not authorization.
5. **Authentication and privacy.** Only administrator-approved emails may register hosts. Hash passwords with a supported password KDF; keep expiring sessions server-side with secure cookie protections. Never hardcode credentials or commit private data, database files, session tokens or passwords. Never send automated emails or introduce email-dependent flows. Guest sign-in requires names and a permanent random invite code. Reveal optional suffixes only after code-qualified recognition. Keep child/adult association and attempt limits. Shared identities never auto-merge: show minimal server-side suggestions, require explicit host selection and guest code-authenticated approval before granting cross-host invitations. Keep host contacts/notes and relationships separate; preserve codes and other relationships on host removal. See docs/family-workspace.md for reversible linking and legacy rollout.
6. **Central persistence and sync.** The shared server and centralized SQLite storage are authoritative, not browser local storage. Node.js 24 uses local SQLite; Cloudflare uses a separate SQLite-backed Durable Object and the same shared application rules. Keep storage chunking transactional and Unicode-safe. Keep all devices synchronized and preserve data across sessions/restarts. Require record versions for host writes and per-adult/event RSVP versions; transact capacity checks and reservations. Reject stale writes without erasing drafts. Do not adopt background refreshes behind an unsaved editor. A multi-replica database change must preserve tenant boundaries and transactional guarantees.
7. **RSVP integrity.** Invite each adult/child explicitly. Children belong to a designated adult and do not sign in separately. Count each invited person individually. Keep invitations, RSVPs and claims event-specific. Prevent overclaiming, release items on decline and preserve existing claims when targets shrink. Close every guest RSVP edit after the UTC calendar deadline; preserve saved responses and claims. Keep removal behavior consistent with README. Complete named attendance/claim dashboards are host-only.
8. **Mobile first.** Every feature, form, modal, menu and fixed toolbar must work on phones with readable sizes, touch targets, safe-area spacing and accessible labels. Keep keyboards and scrolling from obscuring controls. Also verify tablet/desktop layouts and print behavior. Extend the shared controls instead of duplicating them.
9. **Test and document changes.** Use `npm ci` on Node.js 24. Run `npm test`, `npm run test:mobile`, `npm run test:cloudflare` and `npm run format:check` for application changes. Use synthetic isolated databases/browser sessions, never live guests or production endpoints. Cover multiple hosts/events, guests/children, appearance isolation, roles, competing writes and cross-device sync. Add meaningful regression coverage for changed behavior. Update README and security guidance when architecture, features, setup or limits change. Report actual passed/failed/unrun checks and documentation status.
10. **Review and deployment safety.** Work in the existing checkout; do not create a worktree unless explicitly requested. Check the final diff for secrets, private data and unrelated changes. Open a pull request for review. Never merge, deploy, migrate live data or alter production configuration without explicit authorization. Keep CI validation-only unless deployment is separately approved. Cloudflare deployments must target the events-only Worker/database in the owner-selected account, with no existing gatherings routes or bindings. Browser administrator setup must require an owner-configured secret, exact-origin checks, persistent attempt limits and an atomic single-use completion marker. Never allow public first-user ownership claims or use setup to reset an existing administrator. Keep setup credentials out of URLs, logs, browser storage and API responses.

Architecture reference: `server/model.js` owns storage and transactional rules; `server/handler.js` owns the shared authorized API; `server/app.js` and `server/node-store.js` adapt local Node HTTP/SQLite; `cloudflare/worker.js` adapts Cloudflare Fetch and durable SQLite; `public/app.js` owns shared views and editors; `public/style.css` owns responsive styling. Read [README.md](README.md), [docs/security.md](docs/security.md) and [docs/cloudflare.md](docs/cloudflare.md) before changing those boundaries. Keep this file aligned with the implemented system without weakening its privacy or shared-code requirements.

## Household hostname rules

Keep household domains as transactional data in `household_domains`, with permanent retired-name reservations; do not infer surnames, preclaim names for real hosts, change opaque slugs or backfill existing accounts. Validate labels with `server/household-domains.js` and reserve all existing site/platform names, including `themeyers`. Registration must derive the label from the entire household name using the shared normalizer and atomically enforce ownership/uniqueness. No independent domain choice, editor, numbered alternative or host rename is allowed. Reject API overrides/renames. Later display-name edits preserve existing claims. Preserve all prior data and session/setup markers.

`cloudflare/gateway.js` is a stateless exact-host proxy, not another application. Only the reviewed events origin and authoritative active claims (or private anonymous verification probes) may be forwarded. Verify HMAC at the public events edge before using hostname/IP context; strip untrusted private headers. Keep exact Origin CSRF, origin-bound host-only Secure cookies, role/household isolation and generic failures. Never activate sharing/QR for pending names. Keep household login appearance independent from event overrides.

Follow `docs/household-subdomains.md` for verified account inventory, explicit per-host provisioning, missing access, deployment and rollback. No wildcard routing, new cross-account database, namespace/class/object-name changes, open proxy, broad CORS, credential disclosure or live fixtures. Preserve `themeyers.ilymmd.com`, `curly-sun-ef0f` and all other sites/resources. Before pushing a branch/PR, verify events-account production/preview build safety so publication cannot deploy this unapproved feature. Deployment remains separately owner approved. Run the domain API/runtime tests via `npm test` and both original and domain phone/desktop tests via `npm run test:mobile`, plus `npm run test:cloudflare` and format checks.

Automatic routing is an events-only backend service in the existing EventsDatabase alarm, with an atomic `household_routing` outbox and five-minute recovery cron. Never expose its token, probes, receipts or management operations to hosts. Use only the fixed domain account/zone and POST-only absent exact DNS/routes for provisioning; the separately confirmed account-cleanup path may DELETE only verified exclusively owned receipt IDs. Never update/delete/adopt unrelated resources or add wildcard interception. Keep pending claims on opaque sharing until proof/assets/context and current inventory checks pass. The dynamic gateway lookup must be signed and uncached, and the app must independently enforce claim state and probe-only GET paths. Preserve static allowlists and legacy claims. No runtime Worker-settings writes, extra household database, preclaim/backfill, paid upgrades or automatic deployments. Changes to runtime secrets, flags, cron and either Worker are separately deployment-approved.

Both Workers require `global_fetch_strictly_public` for the public verification/forwarding architecture. Derive test runtime compatibility settings from production configs and keep a regression check for this flag. Persist only safe stage/status diagnostic codes; never log transport messages, headers, bodies, credentials or probes. Do not force pending jobs active to bypass verification. Public-network routing must be verified after an explicitly approved deployment; mocked local transport is not that verification.

Private runtime verification traces must contain only fixed stage/outcome codes and numeric status. Never copy raw request envelopes, headers, probe values, response bodies or exception messages into diagnostics. Keep tracing independent from activation and preserve pending protections.

Keep public verification fan-out bounded to two and drain each batch before failure/retry or activation. Preserve every proof, asset, context and final inventory/claim check; concurrency must never activate partial verification.

## Shared editing and background operations

Keep wording, formatting roles and structured ordering independent; resolve platform → household → event and preserve explicit overrides. Use `public/ui-system.js` and escaped copy helpers/catalog for every shared page; regenerate with `npm run copy:catalog`. Never translate protocol identifiers or user data. Layout drag controls require keyboard/touch alternatives and may not separate registries from RSVP. Administrator guest preview is read-only and must not create synthetic live guest data. Administrator page editing uses visual synthetic examples and changes platform defaults only, never individual household/event records. Hosts may edit their own content/formatting, but only administrators may change interface wording/layout. Shared positions/wording apply to every household; preserve existing resolved household formatting transactionally when changing platform formatting defaults.

Use one `public/card-system.js` renderer/editor for all card kinds, shared admin templates and tenant-private templates. Saved cards snapshot source data; source changes must not overwrite them. Preserve existing QR destinations, safe contrast/quiet zone, and common preview/export/print rendering. Do not equate opening a composer or sharing UI with delivery.

Notes stay out of every public/guest/preview/card payload. Phones belong to existing scoped guest/contact records. SMS dispatch stays disabled unless the operator explicitly configures/approves the provider. Keep persistent consent/STOP suppression, IANA-timezone conversion, at-most-one delivery attempt and send-time eligibility checks. Unknown outcomes must not be automatically retried. Use mocked providers only in tests; never buy services or send live messages during validation.

Host removal requires server-side administrator authorization, exact email/domain and current data-revision confirmation. Revoke access/cancel reminders before asynchronous cleanup. Delete only exact resources proven exclusively owned by stored receipts, fail closed on conflicts/incomplete inventory, and permanently retain retired names. Do not test on real accounts. Preserve additive metadata and pending-deletion protections during rollback; `ACCOUNT_CLEANUP_ENABLED=false` pauses cleanup. See `docs/shared-editors.md` for provider setup, privacy boundaries and release/rollback details.

Browser tests must not open a native print/share/email dialog. Intercept only that browser boundary while asserting our generated document and invocation. Keep browser stages visible and bound total execution/cleanup so a stalled browser cannot silently consume the CI job deadline. Do not increase timeouts to hide an unknown hang or skip required runtime checks to release.

## Family workspace

Use server/family-permissions.js for every family read/write/feed/search/download/notification. Keep owner, household administrator, member and kid separate from platform admin. Original hosts retain ownership until a password-confirmed transfer. Child access requires explicit child IDs on a record and every enclosing folder; parent grants never expose restricted children. An assigned chore grants only that chore, never linked private records. Adult role changes cannot be delegated to kids; only owners appoint administrators. Revoke sessions on password, ownership, disabling and removal changes.

Use per-item versions and transactions for lists, retained per-occurrence chore completion/history and private chunked SQLite files (2 MB/file, 20 MB/household). Recipe import accepts bounded public HTTPS structured data only; validate every redirect and enforce public address restrictions in the runtime transport. Never bypass a configured proxy. Family reminders are in-app only, deduplicated and rechecked for permissions, assignment, cancellation, completion, preferences and quiet hours. No external messaging, new storage service or extra cron is authorized by this feature. Keep the additive identity/member tables on rollback; older name-only or single-owner code is not a safe authorization rollback.
